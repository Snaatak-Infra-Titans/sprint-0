> A complete reference guide explaining the purpose of every directory and file in a standard Ansible role, following the [Common Stack](https://galaxy.ansible.com/) convention.

## Overview

An **Ansible Role** is a self-contained, reusable unit of automation that groups related tasks, variables, templates, files, and handlers into a well-defined directory structure. Roles allow you to break large playbooks into manageable, portable components that can be shared across projects and teams.

The directory layout below is the **standard Ansible role skeleton** (generated by `ansible-galaxy role init <role_name>`). Every directory has a specific, conventional purpose — Ansible automatically loads content from these directories when a role is invoked.

---

## Directory Tree

```
roles/
└── <role_name>/
    ├── defaults/
    │   └── main.yml
    ├── files/
    ├── handlers/
    │   └── main.yml
    ├── meta/
    │   └── main.yml
    ├── tasks/
    │   └── main.yml
    ├── templates/
    ├── tests/
    │   ├── inventory
    │   └── test.yml
    └── vars/
        └── main.yml
```

## Directory Reference

### `tasks/`

**The heart of the role.** Contains the main list of tasks to be executed by the role.

- `main.yml` is the **entry point** — Ansible automatically reads this file when the role is applied.
- Tasks are executed in the order they are defined.
- You can split logic across multiple files and include them from `main.yml` using `import_tasks` or `include_tasks` for better maintainability.

```yaml
# tasks/main.yml
- name: Install nginx
  ansible.builtin.package:
    name: nginx
    state: present

- import_tasks: configure.yml
```

**Rule of thumb:** If something *does* something (installs, configures, starts, copies), it lives here.

---

### `defaults/`

**Low-priority default variables for the role.**

- `main.yml` defines variables with the **lowest precedence** in Ansible's variable hierarchy.
- These values are intended to be **easily overridden** by users of the role — either in inventory, playbooks, or `vars/`.
- Think of this as the "public API" of your role: document what users are expected to customize here.

```yaml
# defaults/main.yml
nginx_port: 80
nginx_worker_processes: auto
nginx_user: www-data
```

**Key distinction from `vars/`:** Variables here are meant to be overridden. Variables in `vars/` are not.

---

### `vars/`

**High-priority internal variables for the role.**

- `main.yml` defines variables with **high precedence** — they override most other variable sources (except extra vars passed with `-e`).
- Used for **internal role constants** that should not be changed by users: OS-specific paths, package names, internal flags.
- Not intended to be a public interface.

```yaml
# vars/main.yml
_nginx_config_dir: /etc/nginx
_nginx_pid_file: /var/run/nginx.pid
```

**Rule of thumb:** If a user shouldn't change it, put it in `vars/`. If they should, put it in `defaults/`.

---

### `handlers/`

**Tasks triggered by notifications from other tasks.**

- `main.yml` contains **handlers** — special tasks that only run when notified by another task using `notify`.
- Handlers run **once at the end** of a play, regardless of how many times they are notified.
- Commonly used to restart or reload services after configuration changes.

```yaml
# handlers/main.yml
- name: Restart nginx
  ansible.builtin.service:
    name: nginx
    state: restarted

- name: Reload nginx
  ansible.builtin.service:
    name: nginx
    state: reloaded
```

**Important:** Handler names must exactly match the string used in the `notify` directive of a task.

---

### `templates/`

**Jinja2 template files that are rendered and deployed to target hosts.**

- Contains `.j2` files — plain text files with Jinja2 expressions (`{{ variable }}`, `{% if %}`, etc.).
- Rendered at runtime using role variables, host facts, and inventory variables.
- Deployed using the `ansible.builtin.template` module.
- Retains directory structure — subdirectories within `templates/` are preserved on the target.

```
templates/
├── nginx.conf.j2
└── vhost.conf.j2
```

```yaml
# tasks/main.yml
- name: Deploy nginx config
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    owner: root
    mode: '0644'
```

**Rule of thumb:** If the file needs variable substitution, it's a template. If it's static, it belongs in `files/`.

---

### `files/`

**Static files to be deployed to target hosts without modification.**

- Contains binary files, scripts, certificates, configuration files, or any file that does **not** need variable substitution.
- Deployed using the `ansible.builtin.copy` module.
- Ansible automatically searches this directory when you reference a source file by name (no path needed in most cases).

```
files/
├── sudoers.d/
│   └── deploy_user
├── nginx_status.conf
└── ssl_dhparams.pem
```

```yaml
# tasks/main.yml
- name: Copy static config
  ansible.builtin.copy:
    src: nginx_status.conf
    dest: /etc/nginx/conf.d/status.conf
```

**Rule of thumb:** If the file is copied as-is, it goes here. If it has `{{ variables }}`, it goes in `templates/`.

---

### `meta/`

**Role metadata and dependency declarations.**

- `main.yml` defines **role metadata** consumed by Ansible Galaxy and the Ansible runtime.
- Declares **role dependencies** — other roles that must run before this one.
- Contains author info, supported platforms, Galaxy tags, and the minimum Ansible version.

```yaml
# meta/main.yml
galaxy_info:
  author: your_username
  description: Installs and configures nginx
  license: MIT
  min_ansible_version: "2.14"
  platforms:
    - name: Ubuntu
      versions:
        - focal
        - jammy
  galaxy_tags:
    - web
    - nginx

dependencies:
  - role: common
  - role: ssl_certs
    vars:
      cert_domain: "{{ nginx_domain }}"
```

**Important:** Dependencies listed here are always executed before the role's own tasks run.

---

### `tests/`

**Local test infrastructure for verifying the role in isolation.**

- Contains a minimal inventory and a test playbook to allow the role to be tested independently.
- Used for quick local validation, CI pipelines, or integration with tools like **Molecule**.
- Not deployed to production hosts — purely for role development and testing.

```
tests/
├── inventory        # A minimal hosts file for testing
└── test.yml         # A simple playbook that applies the role
```

```yaml
# tests/test.yml
---
- hosts: all
  roles:
    - role: <role_name>
```

```ini
# tests/inventory
localhost ansible_connection=local
```

**Best practice:** For more comprehensive testing, replace this with a full [Molecule](https://molecule.readthedocs.io/) setup (`molecule/`).

## Variable Precedence Quick Reference

Understanding which variable directory to use comes down to **intended audience and override behaviour**:

| Directory   | Precedence | Who Should Set It     | Overridable by Users? |
|-------------|------------|-----------------------|-----------------------|
| `defaults/` | Lowest     | Role author (defaults) | Yes — intentionally   |
| `vars/`     | High       | Role author (constants) | No — internal only   |

---

## How Ansible Loads a Role

When a role is listed in a playbook, Ansible automatically loads content from directories **in this order**:

1. `meta/main.yml` — resolve and run dependencies first
2. `defaults/main.yml` — load default variables
3. `vars/main.yml` — load role variables (overrides defaults)
4. `tasks/main.yml` — execute tasks
5. `handlers/main.yml` — register handlers (executed at play end when notified)
6. `templates/` and `files/` — made available for `template` and `copy` modules
7. `tests/` — never auto-loaded; manually invoked for testing

## Common Stack Integration

In a **Common Stack** layout, roles are composed together in a `site.yml` or environment-specific playbook:

```
common_stack/
├── site.yml
├── inventory/
│   ├── production/
│   └── staging/
└── roles/
    ├── common/
    ├── nginx/
    ├── app/
    └── monitoring/
```

Each role directory follows the structure documented above. The `common` role typically contains tasks shared across all servers (users, SSH hardening, NTP), while specialised roles (nginx, app, monitoring) layer on top.

## Quick Reference Card

| Directory     | Purpose                                          | Key File      | Module Used          |
|---------------|--------------------------------------------------|---------------|----------------------|
| `tasks/`      | Main automation logic — what the role *does*     | `main.yml`    | Any                  |
| `defaults/`   | Default variables (overridable by callers)       | `main.yml`    | —                    |
| `vars/`       | Internal role constants (not for override)       | `main.yml`    | —                    |
| `handlers/`   | Triggered tasks (e.g., service restarts)         | `main.yml`    | `service`, `command` |
| `templates/`  | Jinja2 files rendered with variables             | `*.j2`        | `template`           |
| `files/`      | Static files copied as-is                        | any           | `copy`               |
| `meta/`       | Metadata, Galaxy info, role dependencies         | `main.yml`    | —                    |
| `tests/`      | Minimal test inventory and playbook              | `test.yml`    | —                    |
